Despliegue gratuito de frontend y backend

Guía paso a paso para publicar app-TiendaWeb-frontend y app-TiendaWeb-backend, configurar MongoDB y Cloudinary, activar CI/CD y verificar la aplicación en producción.

1. Arquitectura recomendada

La aplicación se divide en cuatro piezas. El frontend se sirve como archivos estáticos; el backend ejecuta Node.js y Express; MongoDB almacena los datos; y Cloudinary almacena las imágenes subidas desde el panel.

PiezaOpción recomendadaMotivo
Frontend React/ViteGitHub PagesIntegrado con el repositorio y el workflow CD existente.
Backend Node/ExpressRender Web ServiceDespliegue sencillo desde GitHub y plan gratuito sujeto a límites y suspensión por inactividad.
Base de datos MongoDBMongoDB Atlas M0Clúster gratuito para desarrollo y proyectos pequeños, sujeto a límites del proveedor.
ImágenesCloudinary FreeCDN y almacenamiento de imágenes sin guardar archivos en el servidor efímero.
Importante: las condiciones de los planes gratuitos, límites, regiones y suspensión por inactividad pueden cambiar. Comprueba los precios y límites vigentes antes de usar la aplicación en producción.

2. Requisitos previos

  • Cuenta de GitHub con acceso de escritura a los repositorios.
  • Node.js 20 o superior y npm instalados localmente.
  • Dos repositorios o dos carpetas versionadas: frontend y backend.
  • Cuenta gratuita de Render, MongoDB Atlas y Cloudinary.
  • Una contraseña administrativa segura y un secreto JWT aleatorio.
  • Un dominio opcional. Las URL gratuitas de GitHub Pages y Render funcionan sin dominio propio.

Verificar herramientas en Windows

node --version
npm --version
git --version

3. Preparar los repositorios

Haz este procedimiento en cada proyecto por separado. El repositorio del frontend debe contener `package.json`, `vite.config.js`, `src/`, `public/` y `.github/workflows/`. El backend debe contener su `package.json` y `src/server.js`.

git status
git add .
git commit -m "Prepare production deployment"
git push origin main
No subas secretos: nunca confirmes `.env`, contraseñas, hashes sensibles, tokens ni URLs privadas con credenciales. Aunque un archivo esté en `.gitignore`, revisa siempre git status antes de hacer push.

Si alguna credencial real estuvo en un commit, elimínala del historial y rótala inmediatamente. Cambiar solo el archivo actual no invalida una credencial que quedó en el historial de Git.

4. Crear MongoDB Atlas gratuito

  1. Regístrate en MongoDB Atlas y crea una organización y un proyecto, por ejemplo TiendaWeb.
  2. Crea un clúster compartido M0 en una región cercana al servidor del backend.
  3. Crea un usuario de base de datos con contraseña larga y única. No uses la contraseña de GitHub.
  4. En Network Access, agrega la dirección desde la que se conectará el backend. En plataformas con IP dinámica puede ser necesario permitir 0.0.0.0/0; hazlo solo con un usuario de mínimo privilegio y una contraseña robusta.
  5. En Connect > Drivers, copia la cadena de conexión Node.js.
  6. Sustituye usuario, contraseña y nombre de base de datos. Usa una base como tiendaweb.
mongodb+srv://USUARIO:CONTRASENA@CLUSTER.mongodb.net/tiendaweb?retryWrites=true&w=majority

Guarda esta cadena solo como variable de entorno del backend. El backend crea la colección pedidos si todavía no existe y MongoDB creará las demás colecciones al insertar documentos.

5. Crear la cuenta de Cloudinary

  1. Crea una cuenta en Cloudinary y abre el Dashboard.
  2. Copia el valor CLOUDINARY_URL o anota cloud name, API key y API secret.
  3. Usa esa variable únicamente en el backend. El frontend solo recibe la URL pública de la imagen.
  4. Revisa el uso de almacenamiento y transformaciones desde el panel del proveedor.
Razón técnica: el backend usa Cloudinary para la ruta de subida de imágenes. No dependas del disco local de Render, porque los servicios gratuitos pueden reiniciarse y su filesystem no debe tratarse como almacenamiento permanente.

6. Desplegar el backend en Render

  1. En Render selecciona New + > Web Service y conecta el repositorio de app-TiendaWeb-backend.
  2. Elige la rama main, región cercana y el plan gratuito disponible.
  3. Configura el entorno como Node. El directorio raíz es la raíz del repositorio del backend.
  4. Usa npm ci como comando de instalación si el proveedor lo permite; si no, usa npm install.
  5. Usa npm start como comando de inicio.
  6. Agrega las variables del siguiente bloque sin comillas y reemplazando todos los placeholders.
  7. Despliega y copia la URL HTTPS asignada, por ejemplo https://tu-backend.onrender.com.
PORT=10000
MONGO_URI=mongodb+srv://USUARIO:CONTRASENA@CLUSTER.mongodb.net/tiendaweb?retryWrites=true&w=majority
CLOUDINARY_URL=cloudinary://API_KEY:API_SECRET@CLOUD_NAME
AUTH_JWT_SECRET=SECRETO_ALEATORIO_DE_AL_MENOS_32_CARACTERES
ADMIN_EMAIL=admin@tu-dominio.com
ADMIN_PASSWORD_HASH=HASH_BCRYPT_DE_LA_CONTRASENA
FRONTEND_ORIGINS=https://USUARIO.github.io

Render suele proporcionar el puerto mediante PORT. El servidor del proyecto ya acepta el valor de la variable, pero debes comprobar en los logs que inicia correctamente.

Generar los valores seguros

node -e "require('crypto').randomBytes(32).toString('hex').then(console.log)"
node -e "require('bcryptjs').hash(process.argv[1], 12).then(console.log)" "CAMBIA_ESTA_CONTRASENA"

El primer comando genera AUTH_JWT_SECRET. El segundo genera ADMIN_PASSWORD_HASH. Guarda la contraseña original en un gestor de contraseñas, no en Git.

Comprobar el backend

curl https://TU_BACKEND.onrender.com/
curl -i -X OPTIONS https://TU_BACKEND.onrender.com/api/articulos

La primera llamada debe devolver JSON con el mensaje de API activa. La segunda debe devolver una respuesta CORS válida cuando el origen sea el frontend configurado.

7. Configurar CORS correctamente

El backend permite los orígenes enumerados en FRONTEND_ORIGINS, separados por comas. Después de desplegar GitHub Pages, usa la URL exacta, incluyendo protocolo y sin una barra final.

FRONTEND_ORIGINS=https://USUARIO.github.io

Si el repositorio se publica como proyecto en GitHub Pages, la aplicación estará bajo una ruta como https://USUARIO.github.io/tiendaweb-frontend/, pero el origen CORS sigue siendo solo https://USUARIO.github.io, porque CORS compara origen y no ruta.

Durante desarrollo puedes usar:

FRONTEND_ORIGINS=http://localhost:5173,http://localhost:4173

Después de cambiar variables del backend, reinicia el servicio y prueba una llamada desde el navegador. No uses * como solución permanente.

8. Desplegar el frontend en GitHub Pages

  1. Abre el repositorio de app-TiendaWeb-frontend en GitHub.
  2. Ve a Settings > Secrets and variables > Actions > Variables.
  3. Crea la variable de repositorio VITE_API_URL con la URL HTTPS del backend, sin barra final.
  4. Ve a Settings > Pages y selecciona GitHub Actions como fuente.
  5. Confirma que el workflow CD - Deploy to GitHub Pages está presente.
  6. Haz push a main o ejecuta el workflow manualmente desde la pestaña Actions.
  7. Espera a que terminen los pasos de lint, tests, build y deploy.

El proyecto ya configura la base de Vite como /tiendaweb-frontend/ en GitHub Actions. No abras el sitio con una ruta distinta a la que GitHub Pages muestra en Settings > Pages.

Resultado esperado: la página de login carga, el manual técnico se descarga y el frontend puede llamar a VITE_API_URL sin errores de CORS.

Validación local equivalente

cd app-TiendaWeb-frontend
npm ci
npm run lint
npm run test:ci
npm run build

10. Inicializar empleados

El backend incluye un script para crear los empleados iniciales. Ejecútalo una sola vez después de que el backend tenga acceso a MongoDB.

cd app-TiendaWeb-backend
npm ci
npm run seed:empleados

El script muestra las credenciales iniciales una vez. Entrégalas por un canal seguro y solicita el cambio o rotación de contraseñas según la política del proyecto.

No ejecutes el seed repetidamente sin revisar su comportamiento y la base de datos; podrías crear duplicados o regenerar credenciales.

11. Pruebas de aceptación en producción

  1. Abre la URL de GitHub Pages en una ventana privada.
  2. Inicia sesión con una cuenta de prueba, no con una credencial compartida.
  3. Comprueba que el catálogo cargue desde el backend.
  4. Consulta Inventario, Pedidos y Ventas.
  5. Crea un artículo de prueba, revisa la imagen y elimínalo solo si la política lo permite.
  6. Registra una venta de importe controlado y confirma que aparece en Pedidos.
  7. Prueba una cuenta de vendedor y una de encargado para confirmar los permisos.
  8. Abre las herramientas del navegador y confirma que no hay errores CORS, 401, 404 ni mixed content.
  9. Revisa los logs del backend en Render y el resultado de Actions en GitHub.

Comandos de comprobación API

curl -i https://TU_BACKEND.onrender.com/
curl -i https://TU_BACKEND.onrender.com/api/articulos
curl -i -X POST https://TU_BACKEND.onrender.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"USUARIO_DE_PRUEBA\",\"password\":\"CONTRASENA_DE_PRUEBA\"}"

12. Alternativas gratuitas

NecesidadAlternativasConsideraciones
Frontend estáticoGitHub Pages, Netlify, VercelNetlify y Vercel son cómodos para previews y dominios; revisa límites y configuración de variables. GitHub Pages encaja mejor con el workflow actual.
Backend NodeRender, Koyeb, otros PaaS con nivel gratuitoComprueba disponibilidad regional, suspensión por inactividad, límites de horas y necesidad de tarjeta. El comando debe ser npm start y el puerto debe venir de PORT.
MongoDBMongoDB Atlas M0Es la opción directa porque el código usa MongoDB/Mongoose. Revisa almacenamiento, conexiones y límites del clúster.
ImágenesCloudinary FreeEs la opción ya integrada por el backend. No sustituyas por filesystem local en un servicio efímero.
Recomendación práctica: para este repositorio usa GitHub Pages + Render + MongoDB Atlas + Cloudinary. Cambiar de proveedor solo requiere adaptar comandos, variables y restricciones; no mezcles varios proveedores de backend sin necesidad.

13. Seguridad y mantenimiento

  • Rota cualquier credencial que haya sido expuesta en terminal, documento, issue o commit.
  • Usa un secreto JWT distinto en cada entorno.
  • Usa contraseñas bcrypt y nunca guardes contraseñas en texto plano.
  • Limita CORS al origen real del frontend.
  • Revisa el consumo de Render, Atlas y Cloudinary cada mes.
  • Mantén actualizados Node, dependencias y lockfiles mediante pull requests.
  • Haz copias o exportaciones de datos antes de cambios destructivos.
  • No incluyas secretos en variables VITE_*; esas variables llegan al navegador.

15. Checklist de entrega

  • MongoDB Atlas creado, usuario configurado y conexión probada.
  • Cloudinary configurado sin secretos en el repositorio.
  • Backend desplegado y su endpoint raíz responde.
  • FRONTEND_ORIGINS contiene el origen de GitHub Pages.
  • VITE_API_URL está configurada en GitHub Actions.
  • GitHub Pages usa la fuente GitHub Actions.
  • CI pasa lint, tests y build.
  • CD publica desde main.
  • Seed de empleados ejecutado una sola vez y credenciales entregadas de forma segura.
  • Pruebas de login, catálogo, inventario, ventas, pedidos e imágenes completadas.
  • Credenciales de desarrollo rotadas o confirmadas como no expuestas.
