Despliegue con Render, MongoDB Atlas y Cloudinary

Guía completa para publicar la API de TiendaWeb, conectar la base de datos y habilitar la carga permanente de imágenes desde el panel administrativo.

1. Arquitectura recomendada

ComponenteServicioResponsabilidad
FrontendGitHub Pages, Vercel o NetlifySirve la aplicación React/Vite en el navegador.
BackendRender Web ServiceEjecuta Node.js, Express, autenticación y endpoints de la API.
Base de datosMongoDB Atlas M0Almacena artículos, clientes, pedidos y empleados.
Archivos de imagenCloudinary FreeAlmacena imágenes fuera del filesystem efímero del servidor.

El frontend usa una URL pública del backend mediante VITE_API_URL. Render se conecta a Atlas con MONGO_URI y a Cloudinary mediante CLOUDINARY_URL.

Planes gratuitos: Render, Atlas y Cloudinary tienen límites que pueden cambiar. El servicio gratuito de Render puede suspenderse después de inactividad y tardar unos segundos en reactivarse.

2. Requisitos previos

  • Cuenta de GitHub con el repositorio de app-TiendaWeb-backend.
  • Cuenta de Render, MongoDB Atlas y Cloudinary.
  • Node.js 20 o superior y npm para las pruebas locales.
  • Un dominio o URL pública del frontend para configurar CORS.
  • Una contraseña administrativa segura.
node --version
npm --version
git --version
Regla de secretos: no subas .env, MONGO_URI, CLOUDINARY_URL, JWT, contraseñas ni hashes a GitHub. Configúralos en Render.

3. Preparar el backend local

El backend actual tiene estos scripts relevantes:

ScriptUso
npm startArranca src/server.js en producción.
npm run devDesarrollo local con nodemon.
npm run seed:empleadosCrea los empleados iniciales en la base configurada.
 
cd app-TiendaWeb-backend
npm ci
npm start

El servidor expone la ruta raíz / y las rutas bajo /api. Render debe ejecutar el mismo comando npm start.

4. Crear MongoDB Atlas

  1. Entra en MongoDB Atlas y crea una organización y un proyecto, por ejemplo TiendaWeb.
  2. Crea un clúster compartido M0 en una región próxima a Render.
  3. En Database Access, crea un usuario exclusivo para la aplicación.
  4. Usa una contraseña larga, aleatoria y distinta de la cuenta de Atlas.
  5. En Network Access, agrega el origen de conexión del backend. Si Render usa IP dinámica, puede requerirse 0.0.0.0/0; compénsalo con credenciales fuertes y permisos mínimos.
  6. Abre Connect > Drivers y copia la cadena para Node.js.
  7. Reemplaza los placeholders y usa una base llamada tiendaweb.
mongodb+srv://USUARIO:CONTRASENA@CLUSTER.mongodb.net/tiendaweb?retryWrites=true&w=majority
Contraseñas con caracteres especiales: codifica caracteres como @, #, :, / o espacios dentro de la URL de MongoDB. Usa un generador URL-safe o el equivalente de encodeURIComponent.

Atlas crea las colecciones al insertar datos. El backend también comprueba y crea la colección pedidos durante el arranque.

5. Crear y configurar Cloudinary

  1. Regístrate en Cloudinary y abre el Dashboard.
  2. Copia la variable CLOUDINARY_URL o construye el valor con API key, API secret y cloud name.
  3. No pongas ese valor en el frontend ni en variables VITE_*.
  4. Comprueba el límite máximo de 5 MB usado por la ruta de subida del backend.
  5. Revisa periódicamente almacenamiento, transformaciones y ancho de banda.
CLOUDINARY_URL=cloudinary://API_KEY:API_SECRET@CLOUD_NAME

El backend recibe el archivo en el campo multipart imagen, lo sube a Cloudinary y devuelve una URL pública para guardar en ImagenArt.

6. Generar credenciales seguras

Ejecuta estos comandos desde un entorno local con las dependencias del backend instaladas:

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
node -e "require('bcryptjs').hash(process.argv[1], 12).then(console.log)" "CAMBIA_ESTA_CONTRASENA"

Usa el primer resultado como AUTH_JWT_SECRET y el segundo como ADMIN_PASSWORD_HASH. Guarda la contraseña original en un gestor de contraseñas.

Si alguna credencial real apareció en un commit, documento o terminal compartida, rótala. Eliminarla del archivo actual no la elimina del historial de Git.

7. Crear el Web Service en Render

  1. Abre Render y selecciona New + > Web Service.
  2. Conecta GitHub y autoriza el repositorio de app-TiendaWeb-backend.
  3. Selecciona la rama main.
  4. Si el backend es un repositorio independiente, deja el Root Directory vacío. Si es un monorepo, escribe la carpeta del backend.
  5. Selecciona el runtime Node y el plan gratuito disponible.
  6. Configura npm ci como Build Command.
  7. Configura npm start como Start Command.
  8. Elige una región cercana a MongoDB Atlas y al público principal.
  9. Agrega las variables de entorno antes del primer deploy.
  10. Pulsa Create Web Service y espera a que termine el build.

Valores recomendados

Campo RenderValor
RuntimeNode
Build Commandnpm ci
Start Commandnpm start
Health Check Path/
Auto-DeployAfter CI passes, si el flujo del equipo lo permite

No fijes un puerto estático. Render proporciona PORT y el servidor del proyecto ya lo lee; el valor local de ejemplo no debe trasladarse obligatoriamente a producción.

8. Variables de entorno de Render

En Environment > Environment Variables, crea cada variable de forma individual:

MONGO_URI=mongodb+srv://USUARIO:CONTRASENA@CLUSTER.mongodb.net/tiendaweb?retryWrites=true&w=majority
CLOUDINARY_URL=cloudinary://API_KEY:API_SECRET@CLOUD_NAME
AUTH_JWT_SECRET=SECRETO_ALEATORIO_DE_AL_MENOS_32_CARACTERES
ADMIN_EMAIL=admin@tu-dominio.com
ADMIN_PASSWORD_HASH=HASH_BCRYPT_DE_LA_CONTRASENA
FRONTEND_ORIGINS=https://TU-FRONTEND.example.com

FRONTEND_ORIGINS puede contener varios orígenes separados por comas:

FRONTEND_ORIGINS=https://tu-sitio.vercel.app,https://USUARIO.github.io

No incluyas barra final, rutas internas ni espacios innecesarios. No configures PORT salvo que Render lo indique expresamente.

9. Verificar el backend publicado

Render asignará una URL similar a https://tiendaweb-api.onrender.com. Comprueba primero la ruta raíz:

curl -i https://TU-SERVICIO.onrender.com/
curl -i https://TU-SERVICIO.onrender.com/api/articulos

La primera respuesta debe ser JSON con el mensaje de API activa. Si el servicio tarda después de inactividad, espera el arranque y repite la llamada.

Consultar logs

En Render abre el servicio y revisa Logs. Debes ver conexión correcta a MongoDB y el servidor escuchando en el puerto asignado. Nunca publiques los logs si contienen secretos.

10. Configurar CORS

El backend valida el origen mediante FRONTEND_ORIGINS. Usa el origen exacto del frontend, no la URL del backend.

FrontendValor CORS
Vercelhttps://tu-proyecto.vercel.app
GitHub Pages de usuariohttps://usuario.github.io
Desarrollo Vitehttp://localhost:5173,http://localhost:4173

Si GitHub Pages usa una ruta de proyecto como /tiendaweb-frontend/, CORS sigue usando solo el origen https://usuario.github.io. Después de editar la variable, reinicia el servicio en Render.

11. Configurar el frontend

  1. Obtén la URL HTTPS pública de Render.
  2. En el repositorio frontend, configura la variable VITE_API_URL en el proveedor de frontend.
  3. En GitHub Actions, usa la variable de repositorio VITE_API_URL si publicas en GitHub Pages.
  4. En Vercel o Netlify, configura la misma variable para Production y Preview según corresponda.
  5. Redeploya el frontend después de modificar variables, porque Vite las incorpora durante el build.
VITE_API_URL=https://TU-SERVICIO.onrender.com

No coloques una barra final. La configuración de la aplicación agrega las rutas /api/articulos, /api/clientes, /api/pedidos y /api/empleados.

12. Crear los empleados iniciales

Cuando Render y Atlas estén conectados, ejecuta el seed una sola vez. Desde el Dashboard de Render usa el Shell si tu plan lo permite o ejecuta el comando en un entorno temporal con las mismas variables:

npm run seed:empleados

El script genera empleados iniciales y muestra sus credenciales una vez. Entrégalas por un canal seguro. No ejecutes el seed repetidamente sin revisar primero la base de datos.

13. CI/CD con Render

  1. Conserva el workflow CI del frontend para lint, pruebas y build.
  2. Protege la rama main y exige que el check de CI sea exitoso.
  3. Configura Render para desplegar desde main después de un merge aprobado.
  4. Desactiva deploy automático temporalmente si necesitas controlar una migración de datos.
  5. Después de cada deploy revisa logs, ruta raíz y una operación de lectura.

Para un flujo más estricto, usa un Deploy Hook de Render desde GitHub Actions después de completar las pruebas. Guarda el hook como secreto; nunca lo escribas en el YAML.

14. Pruebas de aceptación

  1. Abre el frontend en una ventana privada.
  2. Inicia sesión con el administrador.
  3. Comprueba que los artículos cargan desde Render.
  4. Prueba Inventario, Pedidos y Ventas.
  5. Sube una imagen menor de 5 MB y confirma que se almacena en Cloudinary.
  6. Crea un artículo de prueba y comprueba que aparece al recargar.
  7. Registra una venta controlada y verifica el pedido.
  8. Prueba una cuenta de encargado y una de vendedor para validar permisos.
  9. Revisa la consola del navegador: no debe haber errores CORS, 401, 404 o mixed content.
curl -i https://TU-SERVICIO.onrender.com/
curl -i https://TU-SERVICIO.onrender.com/api/articulos

15. Seguridad y límites

  • Rota cualquier credencial que haya sido compartida o expuesta.
  • Usa secretos JWT diferentes para desarrollo y producción.
  • No uses la contraseña de MongoDB Atlas como contraseña de administrador.
  • Restringe CORS a los dominios reales del frontend.
  • Cloudinary y MongoDB Atlas deben tener límites y alertas revisados.
  • No guardes imágenes en el disco de Render: el servicio puede reiniciarse.
  • Revisa el consumo de Render: el free tier puede dormir por inactividad.
  • Haz respaldos de MongoDB antes de cambios destructivos.
  • No expongas secretos en variables VITE_*, porque llegan al navegador.

17. Checklist final

  • Clúster M0 de Atlas creado y accesible desde Render.
  • Usuario de base de datos y contraseña configurados.
  • Cloudinary configurado sin secretos en Git.
  • Web Service de Render usa npm ci y npm start.
  • Variables de producción completas en Render.
  • Ruta raíz del backend responde correctamente.
  • FRONTEND_ORIGINS contiene el origen real.
  • VITE_API_URL contiene la URL HTTPS de Render.
  • CI pasa lint, pruebas y build.
  • Login, catálogo, inventario, ventas, pedidos y carga de imágenes probados.
  • Credenciales iniciales entregadas de forma segura.
  • Plan gratuito, límites y suspensión por inactividad revisados.
Despliegue correcto: frontend accesible, backend respondiendo, CORS sin errores, datos persistentes en Atlas e imágenes alojadas en Cloudinary.
