Despliegue del stack Vercel + Render + MongoDB Atlas + Cloudinary

Guía completa para publicar el frontend React/Vite, la API Node/Express, la base de datos y el almacenamiento de imágenes en servicios independientes.

1. Resultado final

CapaServicioEjemplo de URL o valor
FrontendVercelhttps://tiendaweb.vercel.app
BackendRender Web Servicehttps://tiendaweb-api.onrender.com
Base de datosMongoDB Atlas M0mongodb+srv://...
ImágenesCloudinary FreeURLs HTTPS devueltas por la API

El navegador carga el frontend desde Vercel. El frontend llama al backend de Render mediante VITE_API_URL. Render conecta con Atlas mediante MONGO_URI y sube imágenes a Cloudinary mediante CLOUDINARY_URL.

Orden recomendado: primero Atlas y Cloudinary, después Render, y finalmente Vercel. Así puedes configurar la URL real del backend y el origen real del frontend en el lugar correcto.
Planes gratuitos: los límites, disponibilidad y condiciones pueden cambiar. Render puede suspender servicios inactivos; Atlas, Cloudinary y Vercel tienen límites de uso. Revisa siempre las condiciones actuales.

2. Requisitos previos

  • Cuenta de GitHub con acceso al repositorio frontend y al repositorio backend.
  • Cuenta de Vercel, Render, MongoDB Atlas y Cloudinary.
  • Node.js 20 o superior, npm y Git instalados localmente.
  • Una contraseña administrativa segura.
  • Un gestor de contraseñas para guardar secretos.
node --version
npm --version
git --version

Si frontend y backend están en repositorios separados, cada plataforma debe conectarse al repositorio correspondiente. Si están en un monorepo, configura el Root Directory de cada servicio.

3. Seguridad antes de publicar

No subas secretos a GitHub: nunca confirmes archivos .env, contraseñas, tokens, MONGO_URI, CLOUDINARY_URL, JWT ni hashes administrativos.
  1. Ejecuta git status y confirma que no aparecen archivos de entorno.
  2. Revisa commits anteriores si el proyecto ya fue publicado.
  3. Rota cualquier credencial real que haya sido compartida o expuesta.
  4. Configura secretos únicamente en Render, variables públicas del frontend únicamente en Vercel y GitHub Actions.

Las variables que empiezan por VITE_ llegan al navegador. Nunca pongas ahí claves privadas de MongoDB, Cloudinary o JWT.

4. Preparar y probar el backend

El backend actual utiliza Node.js, Express, Mongoose, JWT, Helmet, CORS, rate limiting, Multer y Cloudinary. Sus scripts principales son:

ComandoUso
npm startArranque de producción mediante src/server.js.
npm run devDesarrollo local con nodemon.
npm run seed:empleadosCreación de empleados iniciales.
 
cd app-TiendaWeb-backend
npm ci
npm start

La API tiene una ruta raíz / que devuelve un JSON de estado y rutas bajo /api. Render usará el mismo comando de inicio.

5. Crear MongoDB Atlas

  1. Entra en MongoDB Atlas y crea una organización y un proyecto llamado, por ejemplo, TiendaWeb.
  2. Crea un clúster compartido M0 en una región próxima a Render.
  3. En Database Access, crea un usuario exclusivo para la aplicación.
  4. Genera una contraseña fuerte y distinta de tu contraseña de Atlas.
  5. En Network Access, autoriza el origen de conexión del backend. Si el proveedor utiliza IP dinámica, puede ser necesario permitir 0.0.0.0/0; usa entonces credenciales fuertes y permisos mínimos.
  6. En Connect > Drivers, copia la cadena de conexión Node.js.
  7. Usa tiendaweb como nombre de base de datos.
mongodb+srv://USUARIO:CONTRASENA@CLUSTER.mongodb.net/tiendaweb?retryWrites=true&w=majority
Si la contraseña contiene @, #, :, /, espacios u otros caracteres reservados, codifícala antes de colocarla en la URI.

El backend crea la colección pedidos durante la conexión si no existe. Las colecciones de artículos, clientes y empleados se crean al usarse.

6. Crear Cloudinary

  1. Crea una cuenta en Cloudinary y abre el Dashboard.
  2. Copia CLOUDINARY_URL o prepara el valor con API key, API secret y cloud name.
  3. Guarda el valor exclusivamente como variable privada en Render.
  4. Revisa los límites de almacenamiento, transformaciones y ancho de banda.
CLOUDINARY_URL=cloudinary://API_KEY:API_SECRET@CLOUD_NAME

La ruta del backend acepta imágenes mediante multipart/form-data, campo imagen, con un máximo de 5 MB. La respuesta devuelve ImagenArt para guardarla en el artículo.

7. Generar las credenciales del backend

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
node -e "require('bcryptjs').hash(process.argv[1], 12).then(console.log)" "CAMBIA_ESTA_CONTRASENA"

Usa el primer resultado como AUTH_JWT_SECRET y el segundo como ADMIN_PASSWORD_HASH. La contraseña original solo debe guardarse en un gestor seguro.

8. Desplegar el backend en Render

  1. En Render selecciona New + > Web Service.
  2. Conecta GitHub y selecciona el repositorio de app-TiendaWeb-backend.
  3. Selecciona la rama main.
  4. Si el backend está solo en el repositorio, deja Root Directory vacío. En un monorepo, introduce la carpeta del backend.
  5. Selecciona Node y el plan gratuito disponible.
  6. Configura npm ci como Build Command.
  7. Configura npm start como Start Command.
  8. Selecciona una región cercana a Atlas y al público objetivo.
  9. Agrega las variables privadas antes de crear el servicio.
  10. Inicia el deploy y revisa los logs.
ConfiguraciónValor
RuntimeNode
Build Commandnpm ci
Start Commandnpm start
Health Check Path/
Auto-DeployActivarlo después de probar el primer despliegue

No fijes manualmente PORT. Render proporciona el puerto y el servidor actual ya lee process.env.PORT.

9. Variables de Render

En Environment > Environment Variables, crea cada variable individualmente:

MONGO_URI=mongodb+srv://USUARIO:CONTRASENA@CLUSTER.mongodb.net/tiendaweb?retryWrites=true&w=majority
CLOUDINARY_URL=cloudinary://API_KEY:API_SECRET@CLOUD_NAME
AUTH_JWT_SECRET=SECRETO_ALEATORIO_DE_AL_MENOS_32_CARACTERES
ADMIN_EMAIL=admin@tu-dominio.com
ADMIN_PASSWORD_HASH=HASH_BCRYPT_DE_LA_CONTRASENA
FRONTEND_ORIGINS=https://TU-PROYECTO.vercel.app

Antes de conocer la URL definitiva de Vercel puedes dejar temporalmente el origen de desarrollo, pero actualízalo antes de la prueba final. No uses * como configuración permanente.

10. Verificar Render y Atlas

Cuando Render asigne una URL similar a https://tiendaweb-api.onrender.com, prueba:

curl -i https://TU-SERVICIO.onrender.com/
curl -i https://TU-SERVICIO.onrender.com/api/articulos

La raíz debe devolver JSON indicando que la API está activa. En Render revisa que los logs indiquen conexión correcta a MongoDB.

Errores de conexión a Atlas

  • Comprueba usuario y contraseña de Database Access.
  • Comprueba la codificación de caracteres especiales en MONGO_URI.
  • Revisa Network Access y la región del clúster.
  • Confirma que la variable no contiene comillas añadidas accidentalmente.

11. Configurar CORS después de crear Vercel

El backend compara el origen exacto del navegador con FRONTEND_ORIGINS. Para Vercel usa:

FRONTEND_ORIGINS=https://TU-PROYECTO.vercel.app

Si necesitas previews, agrega orígenes concretos separados por comas:

FRONTEND_ORIGINS=https://TU-PROYECTO.vercel.app,https://rama-git-TU-PROYECTO.vercel.app

No agregues la ruta de una página ni una barra final. Después de cambiar la variable, reinicia o redeploya Render.

12. Desplegar el frontend en Vercel

  1. En Vercel selecciona Add New > Project.
  2. Conecta GitHub e importa app-TiendaWeb-frontend.
  3. Si el repositorio solo contiene frontend, deja Root Directory en la raíz. En un monorepo, selecciona la carpeta correcta.
  4. Confirma Framework Preset Vite.
  5. Usa npm run build como Build Command y dist como Output Directory.
  6. En Environment Variables, crea VITE_API_URL con la URL HTTPS de Render.
  7. Aplica la variable a Production y Preview según la política del equipo.
  8. Publica y copia la URL de producción.
VITE_API_URL=https://TU-SERVICIO.onrender.com

Fuera de GitHub Actions, Vite usa la base /, adecuada para Vercel. La base específica de GitHub Pages no debe utilizarse en este despliegue.

13. Actualizar CORS con la URL definitiva

  1. Copia la URL de producción de Vercel, por ejemplo https://tiendaweb.vercel.app.
  2. En Render cambia FRONTEND_ORIGINS a esa URL exacta.
  3. Guarda la variable y espera el redeploy.
  4. Abre Vercel en una ventana privada y prueba el login.
El origen CORS de Vercel es https://tu-proyecto.vercel.app. No es https://tu-proyecto.vercel.app/ ni incluye /login.

14. Crear empleados iniciales

Ejecuta el seed una sola vez cuando Render ya tenga conexión con Atlas:

npm run seed:empleados

Puedes ejecutarlo desde un Shell disponible en Render o desde un entorno local configurado con las mismas variables de producción. Entrega las credenciales iniciales por un canal seguro y no las publiques.

Antes de repetir el seed, revisa el código y la base de datos para evitar duplicados o regeneración de credenciales.

16. Pruebas de aceptación en producción

  1. Abre la URL de Vercel en una ventana privada.
  2. Inicia sesión como administrador.
  3. Comprueba que Artículos carga datos desde Render.
  4. Prueba Inventario, Pedidos y Ventas.
  5. Sube una imagen menor de 5 MB y confirma que la URL es de Cloudinary.
  6. Crea un artículo de prueba, edítalo y comprueba que persiste tras recargar.
  7. Registra una venta controlada y verifica el pedido.
  8. Prueba las sesiones de encargado y vendedor.
  9. Comprueba el manual descargable y los enlaces públicos.
  10. Revisa la consola del navegador y los logs de Render.
curl -i https://TU-SERVICIO.onrender.com/
curl -i https://TU-SERVICIO.onrender.com/api/articulos

18. Seguridad y operación

  • Rota las credenciales que hayan sido expuestas.
  • Usa un JWT distinto para cada entorno.
  • Conserva MongoDB y Cloudinary solo en Render.
  • Recuerda que todo VITE_* es público.
  • Restringe CORS a Vercel y previews necesarias.
  • No guardes imágenes en el filesystem de Render.
  • Revisa consumo y límites de los cuatro proveedores.
  • Haz respaldos de Atlas antes de borrar o migrar datos.
  • Protege main y exige CI antes de publicar.

19. Checklist final de entrega

  • Atlas M0 creado, usuario configurado y conexión permitida.
  • Cloudinary configurado y probado.
  • Render ejecuta npm ci y npm start.
  • Variables privadas completas en Render.
  • Ruta raíz del backend responde por HTTPS.
  • FRONTEND_ORIGINS coincide con la URL de Vercel.
  • Vercel usa npm run build, dist y VITE_API_URL.
  • CI pasa lint, 14 pruebas automatizadas y build.
  • Login, roles, catálogo, inventario, ventas y pedidos probados.
  • Subida de imagen probada en Cloudinary.
  • Credenciales iniciales entregadas de forma segura.
  • Logs sin errores críticos y límites revisados.
Estado esperado: Vercel sirve la interfaz, Render responde la API, Atlas conserva los datos y Cloudinary conserva las imágenes.
